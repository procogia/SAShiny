# SAShiny — Project Plan (v1.0)

> Status: **phase 1 (contract spec) delivered, pre-alpha**. Repo is private until the first CRAN submission.
> Normative contract: [`spec/CONTRACT.md`](spec/CONTRACT.md). Where this plan and the spec differ, the spec wins.

## 1. Vision

SAShiny lets an **unchanged SAS program** act as the **server** of a Shiny app, while Shiny (R or Python)
handles **only the UI**. The `.sas` file is never edited: everything SAShiny needs lives in a **sidecar YAML**
file next to it. The same program still runs as-is in SAS Studio, Enterprise Guide or batch.

```
┌──────────────────────────┐        ┌────────────────────────────┐        ┌───────────────────────┐
│  Shiny UI (R or Python)  │ inputs │  SAShiny bridge            │ submit │  SAS 9.4 or SAS Viya  │
│  auto-generated or       │ ─────▶ │  YAML contract · validate  │ ─────▶ │  via saspy            │
│  custom modules          │ ◀───── │  session pool · collect    │ ◀───── │  analysis.sas         │
│  tables · plots · log    │ outputs│  datasets / ODS / log      │ results│  (untouched)          │
└──────────────────────────┘        └────────────────────────────┘        └───────────────────────┘
```

Mental model: `ui.R` stays in R/Python; `server.R` becomes `analysis.sas` + `analysis.sashiny.yml`.

## 3. Business cases

### 3.1 Pharma / CDISC — "Interactive review of validated SAS outputs"
- **Problem:** Clinical programming teams own validated SAS programs (ADaM derivations, TLFs). Medical
  reviewers, statisticians and safety teams want interactive slicing (arm, population, cutoff, subgroup)
  but rewriting validated SAS in R/Python triggers revalidation.
- **SAShiny answer:** the validated program stays **byte-for-byte unchanged**. Only the YAML (parameter
  binding) and the UI are new. The SAS log is captured per run for traceability.
- **Value:** interactive TLF review, safety-signal exploration and ad-hoc subgroup analyses without
  revalidating the analysis code; a bridge period while organisations adopt R/Python.
- **Demo:** synthetic ADSL/ADAE (CDISC ADaM naming) → demographics table, TEAE incidence by SOC/PT, incidence plot;
  inputs: population flag, arms, AE date window, minimum incidence, ADSL/ADAE upload or sample data.
- **Watch-outs:** GxP use needs the deployment (not just the package) to be qualified; the package will
  provide run metadata (program hash, YAML hash, inputs, SAS log, timestamps) to support that.

### 3.2 Banking / AML — "Scenario tuning on the existing SAS engine"
- **Problem:** AML transaction-monitoring scenarios and threshold-tuning (above/below-the-line testing)
  live in SAS and sit under model-risk governance. Analysts iterate on thresholds through tickets and
  batch reruns.
- **SAShiny answer:** analysts change thresholds, segments and look-back windows in a UI; the governed
  SAS scenario code runs unchanged; every run is logged with its parameters.
- **Value:** faster tuning cycles, fewer change requests, a clear audit trail of parameters → results,
  no re-approval of code that didn't change.
- **Demo:** synthetic transactions → alert volumes by threshold, alert-to-SAR proxy rates, segment
  comparison plot; inputs: threshold, segment multi-choice, date range, uploaded transaction file.

### 3.3 General SAS shops — "Self-service apps on top of existing SAS"
- **Problem:** Organisations with large SAS estates have reports and macro libraries that only SAS users
  can run; building web front-ends means rewriting logic.
- **SAShiny answer:** wrap any parameterised SAS program as a web app in minutes; one app can host many
  independent programs as tabs/modules.
- **Value:** self-service for business users, modern UI without touching SAS logic, and a staged path
  for teams that later want to move logic to R/Python.
- **Demo:** `sashelp` datasets (cars, class, heart) → filtered tables, SGPLOT charts, PROC report
  HTML, CSV/XLSX download.

## 4. The sidecar YAML contract

Specified in full in [`spec/CONTRACT.md`](spec/CONTRACT.md) and [`spec/sashiny.schema.json`](spec/sashiny.schema.json).
Worked examples: [`examples/`](examples). Summary:

- **Inputs:** `numeric`, `text`, `choice`, `multichoice`, `date`, `daterange`, `dataset`. Each sets named macro variables.
  Rendering is exact and specified: SAS date literals, quoted lists in choice order, counts and so on.
- **Outputs:** `table`, `plot`, `html`, `log`, `download` (csv, xlsx, xpt, sas7bdat, rtf, pdf).
- **Entry points:** `program` (submit the file verbatim) or `macro` (submit the macro library, then call it).
- **Wrapper:** a byte-exact generated preamble and postamble around the untouched program text, with
  sentinel log lines so the log can be scoped and the run status determined.
- **Validation:** schema errors (`E000`), 16 semantic rules (`S001`–`S016`), 14 value rules (`V001`–`V014`)
  and advisory lint (`L001`–`L005`).

## 5. Architecture layers (identical in both languages)

| Layer | Responsibility | R | Python |
|---|---|---|---|
| Contract | Read/validate YAML against `spec/` schema | `sas_contract()` | `sashiny.contract.load()` |
| Lint | Check program ↔ YAML consistency | `sashiny_lint()` | `sashiny.lint()` |
| Engine | saspy session (9.4 / Viya), mock engine | `sas_engine_saspy()`, `sas_engine_mock()` | `engines.SaspyEngine`, `engines.MockEngine` |
| Pool | Bounded session pool, timeouts, recycling | `sas_pool()` | `sashiny.Pool` |
| Runner | Inject inputs, submit, collect | `sas_run()` | `sashiny.run()` |
| Results | Datasets, ODS, log, run metadata | S3 `sashiny_result` | dataclass `Result` |
| Modules | UI + server modules, auto-UI | `sas_program_ui()/sas_program_server()` | `@module.ui program_ui` / `@module.server program_server` |
| App | One-liner + multi-program app | `sas_app(c("a.sas", "b.sas"))` | `sashiny.app(["a.sas", "b.sas"])` |
| Templates | Project scaffolding | `use_sashiny_app()`, golem template | `sashiny new` CLI |

### 5.1 Session pool design
- **R:** `reticulate`/saspy calls block the R process, so the pool runs SAS sessions in **background
  worker processes** (`mirai` daemons), one saspy session per worker. Shiny `ExtendedTask` submits runs
  to the pool; the UI stays responsive. Pool bounds: `min`, `max`, `idle_timeout`, `max_runs_per_session`.
- **Python:** asyncio-friendly pool; saspy calls run in a worker executor; Shiny's
  `@reactive.extended_task` keeps the UI responsive.
- Each run gets an isolated `WORK` cleanup step so users never see each other's data.
- Mock engine implements the same interface so pool, runner and modules are fully testable without SAS.

### 5.2 Lessons adopted from Shiny for Python
- Decorator-style module pairs → mirrored as strict `*_ui()` / `*_server()` pairs in R.
- Explicit reactive roles (`reactive.calc`, `reactive.effect`, `reactive.value`) → each module documents
  exactly which reactives it returns (`result`, `status`, `log`).
- Express vs Core → `sas_app()` one-liner (express-like) and composable modules (core-like).
- Extended tasks for long-running work, with progress and cancel.
- Strong typing (`py.typed`, mypy) mirrored in R with `checkmate`-style argument checks.

### 10.1 Lisbon demo plan (3 days)

The demo date falls before phases 2–4 can be finished to release quality. The demo is therefore cut as
a **tagged pre-release** (`v0.0.1-demo`) built from the same code that continues to release. Nothing is
built only for the demo. Scope, in priority order:

1. **Day 1 (Nov 8–9):** phase 2 core in R **and** Python (validator, renderer, wrapper, mock engine),
   both passing every fixture.
2. **Day 2 (Nov 9–10):** saspy engine in both (single session first, pool behind the same interface),
   auto-UI modules, and the three example apps in one multi-tab app per language.
3. **Day 3 (Nov 10–11):** live dry-run against SAS, results recorded for the offline fallback, and a
   run-sheet that shows the R and Python apps side by side on the same SAS programs.

## 11. Prior art

- `sasr` (CRAN, insightsengineering): SAS sessions and code execution from R via saspy/reticulate.
- `sasquatch` (rOpenSci): SAS in Quarto via saspy/reticulate.
- `saspy`, `swat` (SAS Institute): official Python clients for SAS 9.4/Viya and CAS.
- PharmaSUG 2024 AP-212, "Execute SAS Procs from Shiny Application".

Differentiation: **a declarative sidecar contract that turns an unchanged SAS program into a Shiny server,
with auto-generated, module-based UI, a bounded session pool, and identical R and Python implementations.**
